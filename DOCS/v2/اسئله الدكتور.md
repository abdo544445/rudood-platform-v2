# 1. 🧭 مقدمة توجيهية: كيف تُجيب كمهندس برمجيات محترف أمام الدكتور؟

عندما يسألك أستاذ المادة أو الدكتور:
> *"تكلم لي عن الروت، والكنترول، والموديل، والواجهات في مشروعكم.. وكيف ربطتم الباك إند بالفرونت إند؟"*

### ❌ الإجابة الضعيفة التي تكررها الأغلبية:
> *"الروت هو الرابط في المتصفح، والكنترول يتحكم بالكود، والموديل هو جدول قاعدة البيانات، والواجهة هي الـ HTML، وربطناهم بمكتبة Axios نجيب داتا ونعرضها وخلاص."*  
*(هذه إجابة تجعل الدكتور يعتقد أنك مجرد مستخدم سطحي ولا تفهم المعمارية البرمجية الحقيقية للمشروع).*

### ✅ الإجابة الهندسية القوية (التي سنشرح تفاصيلها في هذا الدليل):
> *"يا دكتور، مشروعنا مبني على **معمارية مفصولة حديثة (Decoupled Client-Server Architecture)**؛ حيث يعمل Laravel 11 كـ **Headless Backend REST API** بنمط الـ MVC، بينما تعمل الواجهات الأمامية كـ **Single Page Application (SPA)** مستقلة ومكتوبة بـ **React 19 + TypeScript**.*  
> *الربط بينهما ليس مجرد مكتبة استدعاء HTTP عادية، بل هو **منظومة تكاملية خماسية الطبقات (5-Layer Integration Ecosystem)** تشمل: معترضات التوكن المشفرة (Axios Interceptors)، إدارة الهوية بدون حالة عبر Laravel Sanctum، بث الأحداث الحية في أجزاء من الثانية عبر WebSockets مع Redis، توحيد البوابة المعمارية العكسية عبر Caddy Gateway لمنع مشاكل الـ CORS، وتطابق عقود البيانات الصارمة عبر واجهات TypeScript."*

# 2. 🛣️ المحور الأول: الروت (Routing System) في الباك إند والفرونت إند والبوابة

الروت (Route) هو **خريطة الطرق وعنوان المورد (Endpoint URI)** الذي يحدد أين يذهب طلب المستخدم وما هي الدالة أو الصفحة التي ستتعامل معه.

في منصة ردود (Rudood V2)، ينقسم نظام الروت إلى **3 طبقات متناغمة**:

```
                  [ متصفح المستخدم Client Browser ]
                                 │
                     (1) روت البوابة الموحدة
                      Caddy Reverse Proxy (:80)
                     /           │           \
       /api/*       /            │            \  أي مسار واجهة
                   ▼             │             ▼
     (2) روت الباك إند           │     (3) روت الفرونت إند
      Laravel 11 API             │      React Router DOM
      routes/api.php             │      frontend/src/App.tsx
                                 │
                            /socket.io/*
                                 │
                                 ▼
                         WebSockets Node.js
```

---

### أ) روت الباك إند (Backend API Routes)
* **المسار في الكود:** [`backend/routes/api.php`](../../backend/routes/api.php)
* **مبدأ الترقيم البرمجي (API Versioning):** جميع المسارات مجمعة تحت بادئة الإصدار الأول `Route::prefix('v1')` لضمان استقرار التطبيقات وعدم تعطل الواجهات عند إجراء تحديثات مستقبلية.
* **أنواع المسارات في الباك إند:**
  1. **مسارات عامة (Public Endpoints):** مثل تسجيل الدخول `/auth/login`، وتجربة المحاكاة `/demo/simulate`، وجلب مقالات المدونة `/articles` و `/articles/{slug}`. تم حمايتها بمحدد معدل الطلبات `throttle:login` لمنع هجمات التخمين.
  2. **مسارات خاصة محمية (Protected Endpoints):** مغلفة بطبقة حماية التوكن `middleware(['auth:sanctum'])`. لا يدخلها أي طلب إلا ومعه ترويسة `Authorization: Bearer <token>`.
  3. **مسارات المشرف الأعلى (Super Admin Routes):** محصورة بميدلوير التحقق من رتبة المدير `middleware(['auth:sanctum', 'role:super_admin'])` مثل إدارة الشركات، ومستكشف قواعد البيانات، وسجل العمليات.

</div>

<div dir="ltr">

```php
// Location: backend/routes/api.php
Route::prefix('v1')->group(function () {

    // 1. Public Routes (Throttled for Security)
    Route::middleware(['throttle:login'])->group(function () {
        Route::post('/auth/login', [ApiAuthController::class, 'login']);
        Route::post('/auth/register', [ApiAuthController::class, 'register']);
    });
    
    // Public Blog CMS Endpoints
    Route::get('/articles', function () {
        return response()->json(['success' => true, 'data' => Article::published()->latest('published_at')->get()]);
    });

    // 2. Protected Store Owner / Agent Routes (Requires Sanctum Token)
    Route::middleware(['auth:sanctum'])->group(function () {
        Route::get('/auth/me', [ApiAuthController::class, 'me']);
        Route::get('/dashboard/metrics', [ApiDashboardController::class, 'metrics']);
        Route::get('/conversations', [ApiConversationController::class, 'index']);
        Route::get('/bot/settings', [ApiBotController::class, 'getSettings']);
        Route::get('/knowledge-base', [ApiKnowledgeBaseController::class, 'index']);
    });

    // 3. Super Admin Protected Routes
    Route::middleware(['auth:sanctum', 'role:super_admin'])->prefix('admin')->group(function () {
        Route::get('/overview', [ApiAdminController::class, 'overview']);
        Route::get('/companies', [ApiAdminController::class, 'companies']);
        Route::post('/companies/{id}/impersonate', [ApiAdminController::class, 'impersonateCompany']);
        Route::get('/audit-logs', [ApiAdminController::class, 'auditLogs']);
    });
});
```

### ب) روت الفرونت إند (Client-Side SPA Routing)
* **المسار في الكود:** [`frontend/src/App.tsx`](../../frontend/src/App.tsx)
* **المكتبة المستخدمة:** `react-router-dom` (الإصدار السادس).
* **كيف يعمل دون إعادة تحميل الصفحة؟**
  يستخدم ميزة HTML5 History API (`window.history.pushState`). عندما ينقر المستخدم على رابط أو يكتب رابطاً جديداً، يلتقط React Router الحدث ويقوم بتبديل مكون الصفحة (Component) في شجرة الـ Virtual DOM فورياً في عدة ميلي-ثانية دون إرسال طلب جديد لتحميل ملف HTML كامل من السيرفر.
* **حارس المسارات المحمية (`ProtectedRoute.tsx`):** مكون خاص يفحص وجود التوكن المشفر وبيانات المستخدم في الـ State والـ LocalStorage. إذا كان المستخدم غير مسجل، يتم توجيهه تلقائياً إلى صفحة `/login` فوراً مع حفظ الرابط الذي كان يحاول الوصول إليه.

### ج) روت البوابة الموحدة (Caddy Reverse Proxy Gateway)
* **المسار في الكود:** [`Caddyfile`](../../Caddyfile)
* **لماذا نحتاج روت البوابة؟**
  يقف خادم Caddy على المنفذ العام `:80`. يقوم بفحص الرابط القادم:
  - إذا بدأ الرابط بـ `/api/*` أو `/webhook/*` أو `/widget/*` يُوجه الطلب داخلياً إلى حاوية لارافيل `app:80`.
  - إذا كان الطلب ترقية لبروتوكول الويب سوكت أو `/socket.io/*` يُوجهه إلى حاوية Node.js `websocket:3000`.
  - أي مسار آخر (مثل `/dashboard`، `/blog`، `/chat`) يُوجهه إلى حاوية الفرونت إند `rudood_frontend:80` حيث يقوم Nginx بإرجاع `index.html` وتفعيل روت React.

# 3. 🎮 المحور الثاني: الكنترول (Controllers Layer) ودورة حياة معالجة الطلب

الكنترول (Controller) هو **العقل المدبر والمنسق** في نمط الـ MVC. وظيفته:
1. استلام الطلب القادم من الروت (HTTP Request).
2. التحقق من صحة المدخلات (Validation).
3. استدعاء نماذج البيانات (Models) أو الخدمات الهندسية (Services مثل الذكاء الاصطناعي RAG والبحث الدلالي).
4. تطبيق قواعد العمل (Business Logic) وتأكيد صلاحيات المستأجر (Tenant Ownership).
5. **إرجاع استجابة JSON معيارية (JSON RESTful Response) مصحوبة بكود حالة HTTP دقيق.**

### 💡 نقطة يسأل عنها الدكتور بشدة: *"ما الفرق بين الكنترول في V1 و V2؟"*
* **في V1 (القديم - Monolithic Blade):** كان الكنترول يقوم بـ `return view('dashboard', $data);` أي يقوم بدمج البيانات مع كود HTML على السيرفر (Server-Side Rendering) ويرسل ملف HTML ضخماً يثقل الشبكة.
* **في V2 (الحديث - Decoupled REST API):** الكنترول **ممنوع قطعياً أن يعيد HTML**! بل يعيد بيانات خالصة بصيغة JSON الخفيفة:
  `return response()->json(['success' => true, 'data' => $data], 200);`  
  مما يسمح للفرونت إند بالعمل بسرعة فائقة وإمكانية ربط تطبيقات جوال (iOS / Android) بنفس الباك إند مستقبلاً دون تغيير سطر كود واحد!

```php
// Real Example from: backend/app/Http/Controllers/Api/DashboardController.php
public function metrics(Request $request)
{
    $companyId = $request->user()->company_id;

    // Execute business analytics queries through Eloquent Models
    $totalConversations = Conversation::where('company_id', $companyId)->count();
    $aiHandledCount     = Conversation::where('company_id', $companyId)->where('handled_by', 'ai')->count();
    $activeCustomers    = Conversation::where('company_id', $companyId)->distinct('customer_identifier')->count();
    
    // Return pure, standardized JSON response
    return response()->json([
        'success' => true,
        'data' => [
            'total_conversations' => $totalConversations,
            'ai_handled_rate'     => $totalConversations > 0 ? round(($aiHandledCount / $totalConversations) * 100, 1) : 0,
            'active_customers'    => $activeCustomers,
            'channels_breakdown'  => $this->getChannelsBreakdown($companyId),
        ],
    ], 200);
}
```

# 4. 🗄️ المحور الثالث: المودل (Models Layer & ORM) وقواعد البيانات

المودل (Model) هو **طبقة الوصول للبيانات والـ ORM (Object-Relational Mapping)** في لارافيل بواسطة مكتبة **Eloquent**.
وظيفته تحويل جداول قاعدة بيانات PostgreSQL إلى كائنات برمجية (PHP Objects) يمكن التعامل معها دوالياً دون كتابة استعلامات SQL معقدة باليد.

### مسار ملفات الموديل في المشروع:
تقع جميع النماذج في: [`backend/app/Models/`](../../backend/app/Models/)

### 🔑 أهم الموديلات وعلاقاتها الهندسية (Relationships):

1. **`Company.php` (قلب معمارية تعدد المستأجرين Multi-Tenancy):**
   - تمثل المتجر أو المنشأة التجارية المستقلة.
   - ترتبط بعلاقة `hasMany` مع المستخدمين (`User`)، والمحادثات (`Conversation`)، وقواعد المعرفة (`KnowledgeBase`).
   - تعزل بيانات التاجر رقم (1) عن بيانات التاجر رقم (2) تماماً.

2. **`User.php` (المستخدمون والمصادقة):**
   - يحتوي على الرتب (`role`: `super_admin`, `company_admin`, `agent`).
   - يستخدم سمة `HasApiTokens` التابعة لـ Laravel Sanctum لإنشاء التوكنز المشفرة.
   - يرتبط بـ `belongsTo(Company::class)`.

3. **`Conversation.php` و `Message.php` (المحادثات والرسائل):**
   - `Conversation` يمثل جلسة شات كاملة مع عميل عبر واتساب أو المتجر.
   - يرتبط بعلاقة `hasMany(Message::class)` لجلب تاريخ الرسائل المتبادلة بالترتيب الزمني.

4. **`KnowledgeBase.php` (قاعدة المعرفة والبحث الدلالي):**
   - يخزن نصوص الأسئلة والكتالوجات وتضمينات الذكاء الاصطناعي المتجهية عبر إضافة **`pgvector`** في بوستجريس (`vector(1536)`).
   - يتم عمل بحث دلالي عبر مشغل المسافة الكوسينية (`<=> Cosine Distance`).

5. **`Article.php` (مقالات المدونة والـ Scopes):**
   - يحتوي على حقول المقال (`title`, `slug`, `summary`, `content`, `category`, `published_at`, `is_published`).
   - يستخدم ميزة **Local Query Scopes** مثل `scopePublished($query)` ليقوم الكنترول بطلب `Article::published()` بكل نظافة واختصار.

</div>

<div dir="ltr">

```php
// Real Example from: backend/app/Models/Article.php
class Article extends Model
{
    protected $fillable = [
        'slug', 'title', 'summary', 'content', 
        'category', 'read_time', 'icon', 'is_featured', 
        'is_published', 'published_at'
    ];

    protected $casts = [
        'is_featured'  => 'boolean',
        'is_published' => 'boolean',
        'published_at' => 'datetime',
    ];

    // Local Scope for Clean Reusable Filtering
    public function scopePublished($query)
    {
        return $query->where('is_published', true)
                     ->whereNotNull('published_at')
                     ->where('published_at', '<=', now());
    }
}
```

# 5. 🖥️ المحور الرابع: الواجهات (Views & Modern React SPA UI)

في الأنظمة التقليدية القديمة، كانت الواجهات عبارة عن ملفات `.blade.php` يدمج فيها كود PHP مع HTML.  
أما في منصة ردود (V2)، تم فصل الواجهات بالكامل إلى **تطبيق واجهة أمامية حديث فائق السرعة** مبني بـ:
* **React 19:** لبناء واجهات تفاعلية قائمة على المكونات (Component-Based UI).
* **TypeScript 5.7:** لمنع الأخطاء أثناء التطوير من خلال فحص الأنواع الصارم (Strict Typing).
* **Vite 6:** أسرع محرك بناء وحزم ملفات (Build Tool) في العالم.
* **Tailwind CSS:** تصميم زجاجي داكن حديث (Dark Mode Glassmorphism) مع دعم كامل للغة العربية (RTL).

### أين توجد الواجهات في مجلد المشروع؟

    - `channels/ChannelsPage.tsx`: ربط قنوات واتساب، سلة، زد، وتليجرام.
    - `public/BlogPage.tsx`: واجهة المدونة العامة ومكتبة المعرفة الذكية.

# 6. ⚡ السؤال الحاسم: هل ربطنا الفرونت إند والباك إند بمجرد مكتبة استدعاء وخلاص؟

عندما يسألك الدكتور هذا السؤال تحديداً:
> *"هل ربطتم الفرونت إند بالباك إند عبر Axios/Fetch فقط وخلاص؟ أم هناك معمارية ربط حقيقية؟"*

### 🎯 الرد القاطع والاحترافي:
> **"لا يا دكتور، ليس مجرد مكتبة استدعاء بيانات وخلاص! لو كان مجرد استدعاء لتعطل النظام عند أول انقطاع، ولظهرت ثغرات أمنية في التوكن، ولأصبح الشات بطيئاً وبدون طابع حي، ولتعطلت المصادقة مع كل تحديث للصفحة.**  
> **الربط بين الفرونت إند والباك إند في منصة ردود هو منظومة هندسية متكاملة مكوّنة من 5 طبقات مترابطة (5-Layer Integration Ecosystem):"**

```
 ┌────────────────────────────────────────────────────────────────────────┐
 │            منظومة الربط والتكامل الخماسية (5-Layer Architecture)           │
 └────────────────────────────────────────────────────────────────────────┘
                                    │
 ┌──────────────────────────────────▼───────────────────────────────────┐
```

### شرح الطبقات الخمس بالتفصيل والأدلة من الكود:

#### 1️⃣ الطبقة الأولى: طبقة البوابة المعمارية الموحدة (Caddy Gateway & Single Origin)
* **المشكلة:** إذا كان الباك إند يعمل على بورت `8000` والفرونت إند على بورت `5173`، يرفض المتصفح الاتصال بسبب سياسة أمان المتصفحات (Cross-Origin Resource Sharing - CORS).
* **الحل الهندسي في مشروعنا:**
  استخدمنا خادم **Caddy Gateway** كبوابة موحدة تقف على بورت `80`. يقوم كادي بتوزيع الطلبات داخلياً عبر شبكة دوكر (Docker Network):
  - مسارات `/api/*` تذهب إلى الباك إند لارافيل `rudood_app:80`.
  - مسارات الويب سوكت تذهب إلى سيرفر نود `rudood_websocket:3000`.
  - باقي المسارات تذهب إلى حاوية فرونت إند `rudood_frontend:80`.
* **النتيجة:** المتصفح يرى التطبيق بأكمله كأصل واحد (Single Origin)، مما يقضي على مشاكل الـ CORS تماماً ويزيد الأمان والسرعة.

#### 2️⃣ الطبقة الثانية: معترضات الشبكة الذكية وحقن التوكن الآلي (`apiClient.ts`)
* **المسار في الكود:** [`frontend/src/services/apiClient.ts`](../../frontend/src/services/apiClient.ts)
* الربط لا يعتمد على مناداة عشوائية بالـ `fetch`، بل قمنا بإنشاء **عميل مركزي معترض (Axios Client with Dual Interceptors)**:
  1. **معترض الطلبات (Request Interceptor):** قبل أن يخرج أي طلب إلى السيرفر، يفحص الـ LocalStorage لجلب التوكن `rudood_token`، ويقوم تلقائياً بحقنه داخل الـ Headers في صيغة:
     `Authorization: Bearer <token>`
     دون الحاجة لكتابة التوكن يدوياً في كل صفحة أو طلب!
  2. **معترض الاستجابات وصائد الأخطاء (Response 401 Interceptor):** إذا انتهت صلاحية الجلسة أو ألغي التوكن على السيرفر ورد السيرفر بخطأ `401 Unauthorized`، يقوم هذا المعترض باصطياد الخطأ فوراً ومسح التوكن التالف وتوجيه المستخدم بسلاسة إلى صفحة الدخول `/login`.

</div>

```typescript
// Location: frontend/src/services/apiClient.ts
export const apiClient = axios.create({
  baseURL: import.meta.env.VITE_API_BASE_URL || '/api/v1',
  headers: {
    'Content-Type': 'application/json',
    'Accept': 'application/json',
  },
  timeout: 30000,
});

// 1. Automatic Token Injection Interceptor
apiClient.interceptors.request.use((config) => {
  const token = localStorage.getItem('rudood_token');
  if (token && config.headers) {
    config.headers.Authorization = `Bearer ${token}`;
  }
  return config;
});

// 2. Global 401 Unauthorized Session Handler
apiClient.interceptors.response.use(
  (response) => response,
  (error) => {
    if (error.response && error.response.status === 401) {
      localStorage.removeItem('rudood_token');
      localStorage.removeItem('rudood_user');
      if (window.location.pathname !== '/login') {
        window.location.href = '/login';
      }
    }
    return Promise.reject(error);
  }
);
```

#### 3️⃣ الطبقة الثالثة: المصادقة المشفرة بدون حالة (Stateless Sanctum Tokens)
* لا نستخدم جلسات PHP التقليدية المبنية على الكوكيز (Cookies & Sessions) لأنها غير آمنة في بيئة الـ SPA المنفصلة وتفشل مع تطبيقات الجوال وتعدد الخوادم (Load Balancing).
* نستخدم **Laravel Sanctum Personal Access Tokens**:
  - عند تسجيل الدخول الناجح، يُنشئ السيرفر رمز توكن عشوائياً فائق الأمان (Cryptographically Secure Token).
  - يُخزن هاش الرمز (SHA-256 Hash) في جدول `personal_access_tokens` في قاعدة بيانات بوستجريس.
  - يُرسل التوكن النصي الصافي للواجهة الأمامية لتحتفظ به محلياً في الذاكرة المشفرة.
  - مع كل طلب قادم، يفك لارافيل التوكن ويتحقق من هوية التاجر وصلاحياته في أجزاء من الميلي-ثانية.

#### 4️⃣ الطبقة الرابعة: البث اللحظي عبر الويب سوكت (Real-Time Bidirectional WebSockets)
* **المسار في الكود:** `backend/websocket/server.js` و `frontend/src/services/websocket.ts`
* في نظام خدمة العملاء والشات المباشر، **لا يمكن الاعتماد على الـ HTTP بمفردها**؛ لأن التاجر لا يمكنه عمل تحديث (Refresh) كل ثانية ليرى إذا كتب العميل رسالة في واتساب!
* قمنا ببناء مسار بث فوري:
  1. رسالة جديدة تصل من واتساب للباك إند لارافيل.
  2. يُطلق لارافيل حدثاً `MessageReceivedEvent` ويُلقيه في وسيط الذاكرة فائق السرعة **Redis**.
  3. يلتقط سيرفر الويب سوكت المكتوب بـ Node.js الحدث من رديس عبر نمط النشر والاشتراك (Pub/Sub).
  4. يقوم سيرفر الويب سوكت بدفع الرسالة فوراً عبر قناة `private-conversation.{id}` إلى متصفح التاجر ومكون `LiveChatPage.tsx` ليظهر الرد في الشاشة في أقل من 50 ميلي-ثانية دون أي استدعاء HTTP أو تحميل!

#### 5️⃣ الطبقة الخامسة: تكامل الأنواع الصارمة وعقود البيانات (TypeScript Data Contracts)
* **المشكلة البرمجية:** إذا قام مبرمج الباك إند بتغيير اسم حقل في الـ JSON (مثلاً من `is_published` إلى `status`)، تتعطل الواجهة الأمامية ويحدث خطأ أبيض في وجه المستخدم (`Cannot read property of undefined`).
* **الحل في منصة ردود:** قمنا ببناء **عقود بيانات متطابقة (Interfaces)** في الواجهة الأمامية تطابق مخرجات الـ API تماماً. محرك TypeScript يفحص الكود وقت البناء (Build-time) ويمنع أي خطأ أو تضارب في الأنواع قبل أن يصل الكود للإنتاج.

# 7. 🎤 بنك الأسئلة المتوقعة من الدكتور مع الإجابات النموذجية السريعة

استخدم هذه البطاقات السريعة للمراجعة قبل دخول قاعة المناقشة:

### س1: ما فائدة فصل الفرونت إند عن الباك إند بدلاً من استخدام Blade؟
> **الإجابة النموذجية:**  
> "الفصل يحقق مبدأ **Separation of Concerns**؛ فالباك إند يركز فقط على منطق الأعمال وقواعد البيانات وحماية النظام، والفرونت إند يركز على تجربة المستخدم وسرعة العرض التفاعلي. كما أن المعمارية المفصولة تجعل النظام قابلاً للتوسع (Scalable) وتسمح بربط تطبيقات جوال (iOS/Android) ونقاط بيع بنفس الـ API لاحقاً دون إعادة كتابة الباك إند."

### س2: أين يتم التحقق من صحة المدخلات (Validation)؟ في الفرونت أم في الباك؟
> **الإجابة النموذجية:**  
> "في الاثنين معاً يا دكتور؛ نتحقق في الواجهة الأمامية (Frontend Validation) لتقديم تجربة سريعة وتنبيه فوري للمستخدم قبل الإرسال، **ولكن الاعتماد الأمني الحقيقي والمطلق هو على التحقق في الباك إند (Backend Validation)** عبر أدوات لارافيل؛ لأن الفرونت إند يمكن تجاوزه بسهولة عبر أدوات مثل Postman أو Curl."

### س3: كيف تعزل بيانات شركة عن شركة أخرى في قاعدة البيانات (Multi-Tenancy)؟
> **الإجابة النموذجية:**  
> "عبر معمارية **Single Database with Tenant ID Isolation**. كل جدول حساس (المحادثات، الرسائل، إعدادات البوت، قواعد المعرفة) يحتوي على حقل `company_id`. وعندما يسجل المستخدم دخوله، يُستخرج الـ `company_id` الخاص به من التوكن المشفر، وتقوم استعلامات الـ Eloquent بفلترة البيانات تلقائياً بناءً على هذا الحقل، فلا يمكن لمستخدم رؤية بيانات شركة أخرى."

### س4: ما هو الـ RAG والـ Vector Embeddings في المشروع؟
> **الإجابة النموذجية:**  
> "الـ RAG تعني **Retrieval-Augmented Generation**. نأخذ كتالوجات المتجر ومستنداته ونقوم بتقسيمها إلى نصوص صغيرة (Chunks)، ثم نحولها إلى متجهات رقمية (Embeddings) عبر نماذج الذكاء الاصطناعي. ونخزن هذه المتجهات داخل قاعدة بيانات PostgreSQL باستخدام إضافة **`pgvector`**. وعندما يسأل العميل، نبحث عن النصوص الأقرب لمعنى سؤاله باستخدام المسافة الكوسينية (Cosine Similarity) ونمررها للذكاء الاصطناعي ليرد بمعلومات دقيقة 100% من كتالوج المتجر دون هلوسة."

### س5: ماذا يحدث لو انقطع اتصال الإنترنت لدى المستخدم أثناء استخدام المنصة؟
> **الإجابة النموذجية:**  
> "بفضل بناء الواجهة كـ SPA مستقلة، تظل الواجهة تعمل ولا تنهار الشاشة. معترض الشبكة في `apiClient` يلتقط خطأ الشبكة (Network Error) ويُظهر رسالة تنبيهية للمستخدم دون فقدان البيانات المدخلة في الـ State، وعند عودة الاتصال يتم إعادة المحاولة تلقائياً."
